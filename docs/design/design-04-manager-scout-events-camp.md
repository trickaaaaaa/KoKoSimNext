決定事項の反映: 転任=**強制転任あり（元祖忠実）** / 指導力=**分野別** / 新入生=**ハイブリッド**

## 1. 監督メタ

### 1.1 監督能力（分野別・キャリアを通じて持ち越す唯一の資産）
| 能力 | 効果 |
|---|---|
| 打撃指導 | 打撃系練習の効率係数 |
| 投手指導 | 投手系練習の効率係数、投手起用のスタミナ見積り精度 |
| 守備走塁指導 | 守備・走塁系練習の効率係数 |
| 育成眼 | 個別指導「見極め」の精度、新入生の隠しパラメータ開示精度 |
| 采配 | 自動進行時の配球・作戦の質、相手の作戦察知 |

- **成長は2階建て**（プレイヤーが意識して管理する対象にはしない）:
  1. **試合経験でゆるやかに自然増**: 練習試合・公式戦をこなすと分野別能力が少しずつ上がる
     （元祖の「練習試合で指導力が上がる」を踏襲）。格上相手・大舞台ほど得られる経験がやや大きい。
     プレイヤーが積極的に伸ばす操作は不要 ＝ 気づいたら練れている
  2. **節目イベントで大きく伸びる**（下記1.1b）: キャリアの物語の起伏として、特定能力がぐっと動く
- 設計書02の練習式の指導力項を、この分野別係数に置き換える

### 1.1b 監督成長イベント（例）
設計書03のイベントシステムに監督成長フラグを持たせ、条件成立で発生。効果はその場の能力上昇。
- **名将との練習試合**: 甲子園常連校などと対戦すると、采配 or 該当分野の指導力が上昇（教えを乞う）
- **大敗からの学び**: 大差negative の敗戦後、悔しさイベント → 弱点分野の指導力が上昇
- **指導者講習会**: オフ（冬）に参加を選ぶと指導力が上昇（費用・時間とのトレードオフ）
- **教え子の訪問**（`mgr_pro_ob`・issue #1615 / 2026-11-25 オーナー決定）: **監督が直接育ててプロ入りした教え子**（教え子名鑑
  `DraftHistory`・転任をまたぐ監督の記録）が来訪 → 采配・育成眼が上昇。学校のOBではない＝「その高校がプロを出したことがあるか」は
  新設校でも転任先でもプレイヤーには分からないため。名鑑が空なら起こさない。確率・効果の式は変えない。
  乱数は名鑑の有無によらず今までどおり引いてから捨てる（引く回数が変わると後ろの名伯楽の抽選がずれる）。
  会話の {player} には名鑑から決定論（母種＋年度の独立ストリーム）で選んだ教え子の名前を入れる。
  **キャリアシム（`CareerEngine.Run`）は名鑑を持たない**ので常に「いる」扱い（`hasProProtege` 既定 true）＝従来どおり発火しキャリアの帯は動かない
  （ドラフトの近似で判定すると帯が動くうえ、名鑑の無い条件を持ち込むだけで検証価値が薄い）
- **甲子園経験**: 甲子園の舞台を踏むと采配が大きく上昇（頂点の空気を知る）
- **名伯楽との出会い**: 稀イベント。優秀なコーチ/部長を得て特定分野が継続ボーナス
- ※いずれも「狙って連打する」ものではなく、プレイの節目で訪れる。イベントはYAMLで追加可能（設計書04 §3）

### 1.2 信頼度と名声（二軸）
| 軸 | 対象 | 上げ方 | 効果 |
|---|---|---|---|
| 信頼度 | 校内（校長・保護者・部員） | 勝敗、怪我対応、学業配慮、選択肢イベント（下の「年度末の総括以外で…」） | 部予算、強化要求の通りやすさ、残留嘆願（**画面には出さない**＝2026-11-24・issue #1603。予算と異動の抽選の中身だけが残る） |
| 名声 | 全国区 | 大会実績、甲子園、教え子のプロ入り、取材 | 新入生の質と数、練習試合の申込、取材 |

- **名声の時間応答（2026-08-26 案C+Dで改定・`CareerEngine.NextFame`）**:

  ```
  g = 4.0×公式戦勝数 + 30×甲子園出場 (+45 全国優勝) + 金星の加点（季上限8）
  g > 0 なら g ← g × (1 − 名声/110)                     … ①逓減（fame_gain_ceiling）
  保持 = min(名声,60)×0.80 + max(名声−60,0)×0.70        … ③維持の難しさ（fame_decay_high_threshold / fame_decay_high）
  名声' = 保持 + g
  名声' > 名声 + 12 なら 名声' = 名声 + 12              … ②年間上限（fame_season_rise_cap）
  名声' −= 取りこぼしの減点 × (1 + 名声/50)             … ④別枠（fame_upset_loss_fame_scale）
  名声' = clamp(名声', 0, 100)
  ```

  **2026-11-10（issue #868）「上げるより維持するのが難しい」**: 旧式は取りこぼしの減点（負のデルタ）を
  勝ちの加点と先に足してから逓減を掛けていたので、合計が正の年は罰まで「×(1−名声/100)」で縮んだ
  （名声80・4勝・格下に1敗: (16−3.5)×0.2＝+2.5。−3.5 が実質 −0.7）＝**名声が高いほど罰が軽かった**。
  - **④取りこぼしは別枠**: 上昇側（勝ち・甲子園・金星）にだけ逓減・年間上限を掛け、取りこぼしは**そのあとに別枠で**引く
    （`FameUpsetModel.SeasonSplit` が金星と取りこぼしを分けて返す）。さらに**名声が高いほど重く**
    `× (1 + 名声/50)`（名声0で×1.0・50で×2.0・100で×3.0）＝無名校の取りこぼしは今までどおり軽く、名門は許されない
  - **③60を超えた分は保持率0.70**（以下は従来の0.80）。名門ほど現状維持に勝ち続けなければならない
  - **採らなかったもの**: 「名門の早期敗退」の減点（試合の段階情報を名声式へ持ち込む配線が要る）と、
    「同ティアでも強さ差がしきい値以上なら取りこぼし」（`MatchDelta` の格下判定の細分化）。
    ①〜④の実測（下）で目標の目安に届いたので見送った
  - **実測**（強さ固定40年・47県の全国＋夏の県予選→甲子園の `SimulateSeason`・30シード・実ゲームの勝数は sim の約2倍なので ×2 でも測った）:
    定常名声（強さ55/65/75/85）は旧 33.6/45.6/61.8/74.4 → 新 31.8/40.2/52.4/61.7（×2勝）。無名校（強さ35〜45）はほぼ不変、
    常勝校ほど下がる。定常に達した年に格下へ1敗すると、その年の名声は**取りこぼし無しより 強さ55で5.7／75で7.3／85で7.8 低い**
    （旧は一律 3.5 を逓減後に引かれ、実質 0.7〜1 だった）。名声の増減は強さ75の常勝校で +2.1（旧）→ −2.1（新）に反転する
  - **残る性質**: 勝てなくなった王朝の崩れ方（100→年1勝を6年で 40 前後）は今までとほぼ同じ（60超の分が速く減るだけ）。
    名声は新入生の質・後援会の寄付・転任オファーに効くので、常勝校の定常名声が下がる分、長期の難易度は上がる

  2026-08-15 案2（減衰0.80／勝4.0／甲30・時定数5年）で「速さ」を入れたが、**線形和のままだと
  名声のレンジを強さ60台の学校が使い切っていた**。原因は「公式戦勝数」の中身が
  **sim（`CareerEngine.SimulateSeason`＝夏の県大会＋甲子園だけ）と実ゲーム
  （`SchoolRecord.OfficialWins` の年差分＝秋の県大会・地区大会・センバツも数える）で約2倍ずれている**こと
  （実測: 強さ55で 1.60勝 vs 2.92勝／強さ65で 2.18 vs 4.93／強さ75で 4.82 vs 9.93。
  計測ハーネス `out/fame-wins-probe`）。定常＝勝数×20 なので強さ65で99（S）に張り付き、
  県大会を制した年は名声がいくつでも1年でSへ飛んでいた（13.4勝×4.0＋30＋8＝**+91.7**）。
  等級は10点刻み（`Tiers.FromStrength`）なので、プレイヤーには「F→D→急にA」としか見えない
  （2026-08-26 監督報告）。

  **勝数の数え方は変えず、上げ方の形で寝かせる**（`OfficialWins` 経路を触らないので実装が局所で済む）:
  - **①逓減**は上昇側にだけ掛ける。定常値が `110g/(22+g)`（2026-11-15 に基準を100→110へ。名声自体の上限は100のまま）になり100へ張り付かない
    （年5勝＝50前後／年10勝＝67前後／年15勝でも90未満）＝**A・S は甲子園を積み重ねた監督のために空けておく**
  - **②年間上限**は**正味の**上昇量を頭打ちにする。帯幅10に対して+12＝1年で動くのは1段強まで
  - どちらも**下降側には効かない**＝王朝も勝てなくなれば一世代で崩れる（100→年1勝を6年で40前後）。
    名声は §2.1 の新入生の質へ直結するので、この減衰が「勝つ→良い新入生→また勝つ」の
    正フィードバックの**ブレーキ**を担う（`FameDynamicsTests`）
  - 育成の典型カーブ（強さ45→55→65→75→75・最後の年に県制覇＋甲子園）での軌跡:
    **7(G) → 16(G) → 28(G) → 40(E) → 52(D)**（改定前は 7 → 17 → 33(F) → 67(C) → 100(S)）
  - **信頼度・指導力（2026-11-15・issue #981）**: 上と同じ `wins` を読む**信頼度**と**指導力**も同じ倍率でずれていた
    （年10勝なら信頼度 +40/年＝2年で100に張り付く）ので、勝数係数を半分にした
    （`trust_per_win` 4.0→2.0・`coaching_growth_per_win` 0.8→0.4。甲子園20・減衰なしは据え置き）
- **番狂わせ加減点は実ゲームにも配線済み（2026-08-15・issue #170）**: 大会ブラケット確定時
  （`GameSession.FoldTournamentRecords`）に自校の各試合の `FameUpsetModel.MatchDelta` を**その時点の自校の強さ**で
  積み（`ManagerService.RecordTournamentUpsets`）、年度末の監督成長で畳み込む（上昇側は季8上限・下降側は頭打ちなし）。
  試合時点で固定するのは、実ゲームの自校の強さがロスター由来で季節ごとに動くため（夏は3年生込み・3月は新チーム）。
  年度をまたぐぶんはセーブ v12 の `managerPendingUpsetDeltas` で持ち越す。
  F校が格上のD校を1回倒すと +3×2段＝+6（旧来は勝利一律の+1.5だけ）＝序盤の「勝ったのに何も変わらない」を消す
- **信頼度は画面に出さない（2026-11-24 オーナー決定・issue #1603）**: トップバー・キャリア画面・経営タブの内訳・年度末の成長の差分・
  イベントの結果行・通知フィードのどこにも「信頼度」の語もランクも出さない（何に効く数値か分からず困惑するため）。
  中身は残す＝**毎年の予算（学校予算＝基本80＋0.8×信頼度。経営タブは基本ぶんと合わせて「学校予算」1行）**と**異動の抽選（§1.3）**だけに効く。
  増減（勝敗・怪我・イベント・約束）は従来どおり。異動の理由が見えなくなる件は別 issue（#1606）。
- **信頼度は試合に効かない（2026-11-24・issue #1603）**: 旧「信頼度→士気→試合」の経路は外した。士気（プレッシャーの負側の緩和の土台）の入力は
  **チーム状態＝結束 U**（設計書23 §3.4）に置き換えた＝設計書02 §3.2。`PlayerMatchResolver.BuildManagerTeam` が `Team.Morale` に結束 U を渡す（自校だけ・AI校は null）。
- **年度末の総括以外で信頼度・名声が動く経路（2026-11-23 オーナー決定・issue #1270 E1/D1・#1467）**:
  資料 `out/economy-proposal-1299.md` §4 の推奨（小さく）。比べる物差しは総括の幅（名声: 1勝 +4・甲子園 +30／信頼度: 1勝 +2・甲子園 +20・無勝 −12）。

  | 入口 | 信頼度 | 名声 | 置き場所 |
  |---|---|---|---|
  | 選手間の選択肢3種（サボり・学年間・目立ちたがり） | 好転 +2／悪化 −2（結束の上下とは別に） | — | `data/events.yaml` の `outcomes:` の `effects:` |
  | エースの肘の違和感（設計書03 §5.3） | **作らない（#1477）** | — | — |
  | テスト週（学業配慮・設計書03 §5.4） | 練習を軽くする +2／いつも通り −1 | — | 同上 |
  | 怪我を押して出場させて悪化 | 1件 −3 | — | `career: trust_play_through_worsened` |
  | マスコミ取材（#1467） | — | +1（＋次の公式戦の自校側プレッシャー +1） | `media_coverage` の `effects:` |
  | 教え子のプロ入り（D1） | — | 1人 +2（1位 +4）・年 +6 まで | `career: fame_per_draft_pick` ほか |

  - イベントの信頼度・名声は**その場で**動く（`EventService.ApplyEffect`・0〜100で止める）。名声は年度末の保持率0.80で目減りする
    ＝定常への効きは総括の上乗せとほぼ同じ（毎年 +2.4 の上乗せで中堅の定常名声が約 +5）
  - **プロ入りの名声は年度末の総括に入れる**（10月の指名で積み、3月の `NextFame` の上昇側へ＝逓減と年上限 +12 を通す。
    積んだ値はセーブに載る）。1人 +2＝公式戦の半勝ぶん、1位＝1勝ぶん。名声→新入生→指名→名声の正のループを強めないため年 +6 で止める
  - sim（`CareerEngine.Run`）にはイベントもドラフトも無い＝`CareerTests`・`FameDynamicsTests` の帯は不変。
    そのぶん**実ゲームの名声は sim より少し高めに出る**（中堅の定常 31→約36）。勝数の数え方のずれ（#981）と同種の既知の差

### 1.3 転任システム（元祖忠実: 強制転任あり）
- キャリア初期は「教員監督」。**毎年3月に転任判定**があり、拒否できない
- 実績（例: 甲子園出場 or 名声閾値到達）で**「フリー監督」資格**を獲得 → 以降は残留自由・他校オファーの選択制（元祖踏襲）
- 信頼度が非常に高い場合、転任判定を「残留嘆願」で回避できることがある（救済、確率制）
- 転任時: 監督能力と名声は持ち越し、信頼度はリセット。育てたチームとの別れがドラマになる
- **部員は学校に所属する**（issue #641・2026-10-10 改定。旧決定「転任先は1年生10人で再スタート」は廃止）
  - 旧校は **AI校として全国に残る**。新設校（全国生成 seed=2026 に無い学校）なら新しい校IDで全国へ追加し、
    率いていた生成校ならその校IDのまま全国へ戻す。旧部員はそのAI校の永続ロスターへ移り、自校の安定IDを
    そのまま選手IDにする＝大会表や対戦で教え子と再会できる
  - 転任先AI校の部員を**自校が引き継ぐ**。転任先は全国から外れ、自校（専用ID −1）として大会に出る＝二重出場しない。
    自校＝専用ID の前提（Shell 約60箇所）はそのまま残し、全国一覧の側に差分（`NationOverlay`＝追加校＋外す1校）を
    重ねて実現する。差分はセーブ v21 に載る
  - AI校の選手は「いまの能力・適性・怪物種別・学年」しか持たないので、自校へ写すときに足りない隠し情報は
    **決定論で推定**する（2026-10-10 ユーザー決定）: 才能上限＝現在値＋新入生と同じ伸びしろ分布×残り学年の割合、
    成長タイプ・性格・練習効率・分野別伸び・怪我耐性は新入生と同じ分布から (校ID, 選手ID) 由来の専用ストリームで引く
    （`TransferRosterConversion`）。逆向き（自校→AI校）は隠し情報を捨て、背番号はAI校側が毎回振る
  - 成績・配色は**学校に付いて回る**（issue #1261・2026-11-22 オーナー決定）。選手IDは学校ごとに別の名前空間
    （AI校は校内で1から・自校は監督のキャリア通算の採番）で、転任で振り直されるので、帳簿のキーも一緒に写す:
    - 去る学校: 在任中の自校の通算帳簿を、そのまま旧校の全国側の学校別通算へ**据える**（旧校のロスターは自校の
      選手IDを引き継ぐのでキーが合う）。在任中の成績が相手校の選手の通算にも出る（#634 と同じ意味）
    - 引き継ぐ学校: AI時代の学校別通算を全国から外し、`TransferRosterConversion.ToManagerRoster` の
      旧ID→新IDの対応表で付け替えて自校の通算にする。今の部員に居ない（卒業済みの）選手の成績は持ち越さない
    - 自校ストアは転任のたびに区切る（#1112。前任校ぶんは `ClosedSchools` に残る）ので、個人記録に前任校の選手は混ざらない
    - 記録画面の歴代大会は**監督の歴代**（`GameSession.History`・自校バケットは転任をまたいで単一）。右の通算カードも同じく**監督の通算**（見出し「監督の通算」・前任校の戦績を含む）。各行に当時の赴任校名
      （`ManagerPostingHistory.SchoolNameAt`）を併記し、学校の記録とは混ぜない
    - 配色は学校の持ち物: 去る学校の配色は旧校（全国での校ID）に残り、引き継ぐ学校は残っていた配色
      （無ければ AI校だった頃の自動割り当て）をそのまま自校の配色にする（`TeamColorProvider`・セーブ v38 `schoolColorOverrides`）
    - セーブ移行（v38）: 率いている学校の全国側の古い通算帳簿と、#1112 より前の転任で区切られず残った名簿外の自校成績は捨てる
- **フリー監督の候補校の数は名声で増える**（issue #869）: 数 = clamp(2, 10, 2 + floor((名声 − 50) / 4))。
  名声50以下は2校、70で7校、82以上で10校（`career.free_agent_offer_*`＝下限2・上限10・基準50・刻み4）。
  `BecameFreeAgent`（フリー化資格を得た年）と `FreeAgentOffer`（以降のオファー）の両方で同じ式。
  刻みはキャリアシム（80シード×30年・フリー期963年分）の名声分布に合わせた: フリー期の名声は中央値61・95%点86・最大88
  （逓減で100には張り付かない）なので、刻み5だと上限10（名声90）には誰も届かない。刻み4で、フリー期の約10%が10校、
  キャリア全体の約6割が一度は10校に届く。乱数は従来の独立ストリームのまま＝低名声の2校は改定前と同じ学校。
  候補が多いので、赴任先を選ぶモーダルは「候補10校＋残留」の11行がスクロールなしで見える大きさにする（tokens.uss の `--xt-*` 寸法）
- ゲーム的意味: フリー化までが「修行編」。弱小校を渡り歩いて指導力を磨き、フリー化後に本拠地を定めて王朝を築く、というキャリア曲線を作る

### 1.3a マネージャー（NPC）の入れ替わり（issue #1430・2026-11-22 ユーザー決定）
- イベント会話の `who: team_manager`（出番最多）の立ち絵を、自前生成の10人（`Assets/UI/Images/portraits/team_manager/tm01〜tm10.png`）から選ぶ固定の1人へ差し替えるのではなく、**学年を持って入れ替わる人**にする
- 赴任すると1人付く。見た目（10人のどれか）は無作為:
  - 新設校で始めたとき（はじめから）: **1年生**（部員が1年だけなので）
  - 転任で既存の学校に赴任したとき: **2年か3年**（無作為）
- **3年の夏が終わったら引退する**。部員の3年と同じタイミング（夏の敗退／優勝で3年が引退する場面・`summer_retirement_*`の直後）

- **引き継ぎイベント**（`team_manager_succession`・data/events.yaml）を3年引退の会話の直後に積む。引退する側
  （`who: team_manager_outgoing`）と新しい側（`who: team_manager`）の両方が話す
- **同じ見た目が続くことはない**: 新しいマネージャーの見た目は直前のマネージャーと必ず違う（転任で替わるときも、
  前の学校のマネージャーと違う）。新設校スタートは前任が居ないので制約なし
- 状態は `Manager.TeamManagerPortrait`（1〜10）・`Manager.TeamManagerGrade`（1〜3）・
  `Manager.OutgoingTeamManagerPortrait`（入れ替わりの直後だけ引き継ぎイベントの立ち絵に使う）。進級は年度替わり
  （部員の進級と同じ年次）、抽選と入れ替えは `TeamManagerLifecycle`（engine/Career）に集約
- 抽選はドラフトと同じ扱い＝母種から Fork した専用ストリームで引き、本編の乱数列・帯の指紋を乱さない（不変条件#2）
- セーブ v39。旧セーブはマネージャーという状態自体を持たないので、読み込み時に「転任で既存の学校に赴任したとき」と
  同じ扱い（2年か3年を無作為に1人）で埋める（母種から Fork した専用ストリーム＝同じセーブは毎回同じ人になる）

### 1.4a 年契約（毎年かかる継続契約）

施設・練習道具・備品が**買い切り**で効果が累積するのに対し、年契約は**毎年払い続ける**契約で、
**いまどの段で契約しているかだけが効く**（Lv2 の年額と効果が Lv1 を置き換える＝累積しない）。
解約（段を下げる）の操作はいつでもできるが、**段が下がるのは年度末の総括の後**（`ContractSet.ScheduleCancel`→総括の後に `ApplyScheduled`。
それまで効果は残り、その年の年額は必ず引かれる。年額を払わずに1年分の効果を得る穴を塞ぐ・issue #1298・オーナー決定 2026-11-21）。
予約は取り消せ、セーブに載る。段を**上げる**のはすぐ効く。更新イベントの「やめる」も同じく年度末の予約になる。前払いは無く、**年度末の総括（第46週・
`SeasonCalendar.ProspectConfirmWeek`）にまとめて部費から引かれる**（`CareerEngine.ApplyResults`。年度頭ではない）。
年に1回、その直前に更新イベントで見直せる（下の「年度末の更新イベント」）。ただし**スカウト網だけは別**で、
スカウトの一年の頭（夏の大会後）の会話で決める（§2.4「スカウトの一年の入口」・issue #1064）。

### 2.1 受動枠（毎年のメイン供給）
- 3月に入部予定者が確定、4月仮入部（能力は「？」、観察と育成眼で徐々に判明）
- 人数: 基準10人前後（実装は 8〜13人の抽選＝`intake_mean 10 / sd 1.5 / min 8 / max 13`）。
  **人数は名声で増やさない**（監督決定 2026-08-11）。名声・スカウト網が動かすのは**質だけ**で、
  強豪になっても入部者が増えるわけではない（設計初稿の「± 名声・前年実績・地域補正」は人数には適用しない）
- **才能生成モデル（重要・金太郎飴回避）**: 名声が決めるのは各能力値ではなく**選手1人の総合力（配る才能の総量）**。
  1. 名声から選手の総合力の期待値を決める（名声Cの学校ならC相当の総ポイント）。ここにばらつきを持たせる。
     **写像（2026-11-15・issue #1031 で再校正。2026-08-15 案Dの骨格「名声が高ければ新入生にB/Aが入ってよい」は維持）**:
     knee(65)以下は**恒等**＝`talentCenter = 名声`。ただし**下限は `talent_center_default`(32)**（2026-11-16・issue #1043＝
     `talentCenter = max(32, 名声)`。下限が無いと初期名声10の新規ゲームで中心10＝総合力抽選の下限に張り付き、
     「自校がFから抜け出せない」が低名声側で戻った）＝名声0〜32→中心32(F相当)／32〜65→名声のまま。knee超は指数飽和カーブで cap(knee+span=78) へ頭打ち＝
     `talentCenter = cap − span×e^(−(名声−knee)/tau)`（`roster.fame_talent_center_knee / span / tau`）
     ＝名声0→32(F・下限)／10→32(F・下限)／20→32(F・下限)／40→40(E)／55→55(D)／60→60(C)／80→72(B)／100→75.7(B。SD8 なので上位個体はA)。
     旧写像（`talentCenter = 32 + 50×(1−e^(−名声/50))`＝案D）は Default(32) を基準に低〜中名声帯から
     立ち上がる形で、**名声のランクより新入生が1〜2段強く出ていた**（例: 名声D(50〜59)の学校にAI B校
     相当の新入生が入る＝issue #1031 の実測）。knee以下を恒等にしたことで「名声のランク≒新入生の中心の
     ランク」が低〜中名声帯で厳密に成り立つようにした。頭打ち（knee超）はそのまま残し、暴走の抑えは
     §1.2 の名声減衰が担う。実測表（名声20/40/60/80/100×スカウト0/Lv3、AI校ティア別新入生平均との比較）は
     `out/roster-fame-recruit-mapping-1031.md`。
     **身体系（走力・地肩・スタミナ）の中心も 0.75 の傾きで連動する**（`roster.physical_talent_slope`。
     設計書01 §1.1b-2 の但し書き）。連動させないと B/A の新入生が「打撃Aで走力E」になり、機動力・肩・球速の
     天井でチームが C で頭打ちになる（AI校は `StrengthTeamFactory` で身体系が強度連動＝自校だけ天井が低い非対称だった）
  2. 総ポイントを各能力へ**ランダムな重み付けで凸凹に配分**する（均等割りにしない）。
     → 総合Cでも「ミートB・走力D・肩A・守備E」のように内訳に個性が出る
  3. 配分の偏りの強さ自体もばらつかせる → たまたま平均的に配れた「オールC型」も自然に混じる
- 才能上限・伸びしろ（設計書01）も同様に分野別で凸凹に配る → 現在値だけでなく伸び方にも個性
- まれに分布の外れ値として「怪物」（突出した総合力／一芸特化）が出現する。**名声とは関係ない**
  （2026-11-23 オーナー判断・issue #1468。初稿の「名声で出現率がわずかに上がる」は取り下げ）。出る道は2つ:
  ①受動枠の新入生に**たまに無条件で**1人混じる（年4%・`persistent_roster.phenom_own_intake_rate_per_year`）
  ②**スカウトの候補**（§2.4）に混じり、勧誘に成功すると入部する（候補1人あたり0.5%・`phenom_scout_candidate_rate`）。
  型（剛腕/超技巧/スラッガー/韋駄天/鉄砲肩/総合型）と能力帯は AI校の怪物（OPEN-QUESTIONS Q20）と共通。
  怪物という素質そのものはどの段でも見せない（§2.4）。実測は Q20 決定6 の改訂を参照
- スカウト年契約（元祖踏襲）: なし / 地元 / 広域 の3ランク。契約金は年払い
  - 効果1: 新入生の**総合力の期待値**が上振れ（内訳の凸凹は維持）
  - 効果2: 入部予定者の隠しパラメータの事前開示精度が上がる

### 2.2 能動勧誘枠（寮で解禁、少数）── issue #867 で §2.4「スカウト」へ統合・廃止

旧実装（issue #588）は寮Lv1で年2名の勧誘枠を解禁していたが、**監督が狙って探す**遊び
（欲しい分野を選ぶ・段で見える情報が増える・進路希望）を一本化するため、年契約「スカウト網」の段
が持つ枠（§2.4）へ置き換えた。寮は「候補の距離の減点を打ち消す」効果だけを残して存続する
（§1.4a・§2.4 の `dorm_distance_relief`）。中学生リスト・成功率モデルの考え方自体は §2.4 が継承している。

### 2.3 詰み防止
- ポジション配分は原則ランダムだが、捕手のみ最低保証（部に捕手適性が枯渇しない下限補正）
- 補正の強度はバランス検証で調整（硬派さを損なわない最小限に留める）

**実装（#587）: 3月確定 → 4月仮入部**

- **確定週は3月1週目**（`SeasonCalendar.ProspectConfirmWeek` = 第46週）。生成そのものは年度替わりで
  呼んでいた `ProspectGenerator.Intake` と**同じ入力・同じ乱数消費**で、`RosterLifecycle.ConfirmIncoming`
  へ切り出して**確定を前へ倒しただけ**（`ProspectSplitTests` が「2段に分けた結果＝従来の1段生成」を1ビットで固定）。
  人数の抽選規則（`intake_mean/min/max`）も才能の配り方も変えていない
- **`existingNames` の落とし穴**: 年度替わりの③は「卒業を済ませた後のロスター」の氏名列を渡している。
  3月時点ではまだ卒業していないので、そのまま渡すと下の名前の重複回避がずれる。
  **卒業後に残るのは現1・2年だけ**なので `Grade <= 2` で絞れば順序まで含めて同一列になる
- **年度の総括も3月へ前倒しした**（監督決定 2026-08-11）。総括（名声・信頼度・指導力・部費収入・年契約の年額）を
  4月のままにすると、3月時点の名声は**まだ今年度の夏・秋を織り込んでいない**ので
  「甲子園に行った年の実績が新入生に効くのが1年遅れる」。総括はその年度の大会が全部終わった後（3月）に回し、
  4月側の呼び出しは二重適用ガードで no-op になる（3月を跨がずに年度替わりへ来た進行の取りこぼし防止として残す）
- **効果2（事前開示精度）**: スカウト網の段が `ContractTier.ProspectDisclosure`（0〜1）を持ち、
  未契約=0「なし」／Lv1=0.15「ほとんど？」／Lv2=0.45「一部見える」／Lv3=0.75「かなり見える」。開示は
  ①推定カテゴリ強さに乗る誤差σ（`scouting.estimate_sd_max/min`＝20→4）②隠しパラメータ1項目が判明する確率
  （`scouting.reveal_min/max`＝0.05→0.85）の2つへ写す（`ProspectScouting`）。実測（Lv1→Lv3）で
  「？」の平均は 3.3個 → 1.2個 まで減る
- **見立ての抽選は生成とは別ストリーム**（不変条件#2）。スカウト網の段を変えても**来る選手は1ビットも動かず**、
  変わるのは「どこまで見えるか」だけ（受け入れスクショの `sameProspects=True` で確認）
- **未契約（開示0）は見立てそのものを出さない**。開示0の推定は誤差σ20でほぼ雑音なので、
  色付きランクとして出すと画面が嘘をつく＝一覧も詳細も「？」で通す
- **効果1（質）の効き幅の実測**（3,000コホート・約3万人、talentCenter 32→35→38）:
  平均能力 34.96 → 36.68 → 38.41／打撃力 32.07 → 34.27 → 36.49／投手力 29.30 → 30.48 → 31.68。
  効くのは平均より**当たりの頻度**で、最良軸がC以上の選手の割合が **2.78% → 3.99% → 5.74%**、
  B以上が **0.18% → 0.31% → 0.50%** と倍化する（1学年10人なら「C以上が3.6年に1人」→「1.7年に1人」）。
  走力の伸びが小さい（40.25→41.81）のは走力・肩・スタミナが**身体系＝名声独立**で配られるため
  （※2026-08-15 案D で身体系中心は 0.75 の傾きで連動するようになった。この実測は改定前の値）。
  名声換算では **Lv3（+6）≒ 旧写像の名声60〜100 相当**（旧: Fame30→+5.06／Fame100→+7.71・上限+8。
  新写像では名声8前後に相当＝スカウト網の相対的な重みは小さくなった）で、両者は加算される
- **名声とスカウト網が食い合うことはない**（実測で確認・2026-08-11）。talentCenter は
  `TalentCenterFromFame(fame) + ScoutTalentAdd` の**単純な和**で、頭打ち（`fame_talent_center_cap`＝
  knee+span）がかかるのは**名声側だけ**。総合力の抽選 `clamp(Gaussian(center, 8), 10, 90)` の上限90が
  効き始めるのは center 80 付近（実測: center80で10.4%・88で40.0%が切り詰められる）。
  **2026-11-15（issue #1031）再校正後は cap=78（knee65+span13）**で、名声100＋Lv3でも 75.7＋6＝81.7と
  上限90にまだ余裕がある（旧写像span50では32+50+6=88で切り詰めが効き始めていた）。
  **スカウト網の上乗せ（Lv3＝+6）は、写像の低〜中名声帯が恒等になったことで単独でも「同じ段の中の
  上振れ、上がっても最大1段」に収まる**（tier幅10に対し+6は常に1段以内。旧写像は既にtalentCenterが
  1〜2段上振れしている上にスカウトが乗るため、合計2段以上の過剰上振れになっていた＝issue #1031の
  実測はスカウト網Lv3込みで観測されたもの）。この整理によりスカウト網自体の係数（0/3/6）は変更不要。
  むしろ**名声が高いほどスカウト網の見返りは大きい**（C以上率の増分は Fame0 で +2.84pt、
  Fame100 で +6.58pt。閾値をまたぐ裾の量が増えるため。この実測は旧写像時点のものだが、
  「高名声ほど見返りが大きい」という定性的な結論自体は閾値の裾が厚くなる構造から変わらない）
- ただし**伸びしろ余地（上限−現在値）はごくわずかに縮む**（26.72 → 26.34・実測 −1.4%）。
  能力上限が99でクランプされる分だけで、上限そのものは 58.5 → 66.2 と上がる＝完成形は必ず上
- **見立ては選手に触れない**（`ProspectScouting` は純関数で能力を書き換えない）＝スカウトが読み違えても
  入部する選手は変わらない。4月に入部したら実値が見え、`IncomingClass` は選手の実体を手放して
  見立てだけを残す（セーブに二重に載せない）。**入部した学年はスカウト画面に載せない**（2026-11-24 オーナー決定＝
  入部済みの子が「入部予定者」に並ぶと紛らわしい。1年生は選手一覧で見られる。見立てと実際を並べる答え合わせは廃止）
- **旧セーブ（v4以前）**は予定者を持たないので、4月に進めると `AdvanceYear` の従来経路
  （`incoming=null`＝その場生成）へそのまま落ちる

**実装（#589）**: 投手供給の下限（#377 `EnsurePitcherSupply`）と同型で
`ProspectGenerator.EnsureCatcherSupply` を新入生コホートに掛ける。

- **境界**: 「捕手として読める」＝捕手適性 ≥ `roster.catcher_aptitude_floor`（既定 **50**）。
  判定は `CatcherRoleResolver` にしか置かない（閾値のコピーを各所に書かない）。
  50 は `fielding.aptitude_neutral`＝適性補正が付かない点（×1.0）で、これ未満は
  「捕手に置くと不利補正が付く＝不慣れ」。投手役が**比較**（投手適性 vs 最良守備適性）なのに対し、
  捕手は8守備枠の1つ＝誰かが必ず座る枠なので**絶対の下限**で読む
- **効かせ方**: 読める選手が0人のコホートでだけ、捕手適性が最も惜しい1人を境界ちょうどまで引き上げる。
  乱数を使わない決定論操作（不変条件#2）で、**能力（Catching / ThrowAccuracy 等）は底上げしない**
  ＝「その年は捕手が居ない」苦しさは絵に残る
- **候補から投手役を外す**: 捕手適性を上げると最良守備適性が上がり投手判定（`LeansPitcher`）を割るため、
  投手を持ち上げると直前の `EnsurePitcherSupply` が保証した投手供給を壊す
- **実測（下限50）**: 発動率は新入生コホート（8〜13人）の **0.122%**（40,000コホート）。
  参考に閾値を上げたときの発動率は 55→0.69% / 58→1.68% / 60→2.72%（投手版の実測は 2.12%）。
  下限50は「ほぼ発動しない保険」＝§2.3 の『最小限』に収まる
- **AI校には入れない**: AI校は1学年11人×3学年＝33人の永続ロスターから毎回選抜するため、
  ロスター全体で読める捕手が0人になる確率は 20,000校の実測で **0件**（ロスター最高捕手適性の最小値63）。
  `PersistentRosterCoefficients` に `CatcherCountFloor` は置かない
- 参考: 下限が効かない通常のコホートでも、実際に捕手へ就く選手の適性は中央66・p5=37・p1=25
  （`RosterTeamBuilder` は捕手単体でなく**守備8枠の実効守備力の総和**を最大化するので、
  コホート最良の捕手適性の持ち主が捕手に就くとは限らない＝設計どおり）
- **AI校の守備位置は肩も見る（issue #767・2026-11-03）**: `AiTeamBuilder.AssignFieldPositions` の割当重みは
  「実効守備力＋打撃総合×`field_slot_batting_weight`＋**肩Lv×位置別重み**（`field_slot_arm_weight_*`）」。
  重みは 捕手0.6／遊撃0.6／右翼0.5／三塁0.4／中堅0.3／二塁0.2／左翼0.1／一塁0。実測（seed 2026・600校・年度3）:
  先発の肩の中央値 遊撃47→53／右翼48→53／一塁47→44／左翼48→44（旧は全位置48前後で同じ）。守備・打撃の総和はほぼ不変
  （先発守備平均 49.59→49.56）。**並べ替えの上限はチーム内の肩の幅で決まる**（先発8人の肩の最大−最小が平均18）＝
  重みを上げても遊撃の肩は+10程度で頭打ちで、D校以下に肩75超の遊撃手はほぼ生まれない。自校は対象外（守備位置はプレイヤーが決める）
- **AI校の肩の個人差σ＝12（`roster.ai_arm_sd`・issue #767）**: 旧は全能力と同じσ6で、自校の新入生の身体系（`physical_sd` 12）の
  半分だった。σだけ12へ揃え中心（学校の強さ）は据え置き。送球精度は同じ標準正規値からσ6で作る（旧値と1ビット一致）。
  位置別重みと合わせた実測: 先発の肩の中央値 遊撃60／右翼57／捕手57／一塁37／左翼39、D校遊撃手の肩75以上 30%（σ6では4%）、
  C校 64%。`simulate-tiers` の得失点はσ6と±0.2点（誤差内）。エース球速は D校の中央値 137.4→137.8（肩から球速を推定する
  野手兼投手がエースになる校が出る）

### 2.4 スカウト（欲しい選手を探す・見立てる・口説く・issue #867）

**オーナー決定（2026-11-09）に基づく最終仕様。** 旧「年契約を払うと入部予定者が少し見える」（§2.1 効果2）
と旧「寮の能動勧誘」（§2.2・廃止）を、「監督が狙って探し、見立てて、口説く」遊びへ作り直した。

#### 受動枠との関係
入部の総数は今どおり**年8〜13人**（§2.1・名声で増やさない）。そのうち**スカウト枠の人数分だけ**を
スカウトが口説き落とした候補と差し替える。口説き損ねた分は通常どおり受動枠の自動の子が入る＝
**失敗しても人数は詰まらない**。受動枠の生成乱数は動かさない（候補・見立て・訪問・成否は別ストリーム
＝`ScoutingTests.Scouting_DoesNotDisturbPassiveIntake` が固定）。

#### 枠と段ごとの開示
枠の数と「見えるもの」は年契約「スカウト網」の段が兼ねる（§1.4a）。

| 段 | 枠 | 開示 |
|---|---|---|
| 未契約 | 0人 | スカウト自体が起きない |
| Lv1 | 2人 | 寸評だけ |
| Lv2 | 3人 | 寸評＋打・守・走・投の4分野ランク |
| Lv3 | 4人 | 寸評＋4分野ランク＋個別能力のランク |

候補リストは**枠の約3倍**（`scout.candidates_per_slot`=3）が届く。隠し素質（成長タイプ・伸びしろ・怪物）は
**どの段でも見せない**（入部後の育成眼・気づきの楽しみに残す）。段は候補リストを作った時点で凍結し、
後から契約を上げても「もう見ているリスト」の見え方は変わらない（受動枠の事前開示と同じ約束）。

#### 寸評
能力から決定論で文章を作る（文言の正典は `data/scout-blurbs.yaml`）。ノイズ入りの4軸（打/守/走/投）の
最大値から軸と水準（高/中/低）を選び、対応する語彙から1文を引く（`ScoutModel.PickBlurb` /
`ScoutBlurbPhrases`）。**段が低いほど見立てのノイズが大きい**（`scout.report_noise_sd_tier1/2/3`＝
18→10→4）ので、Lv1 では寸評が実態と食い違うことがある。段を上げるほど当たりやすくなる。

#### 探す分野
分野（投球／打撃／守備走塁／おまかせ）を選ぶと、生成する候補プールをその分野の強さ（ノイズ付き）で
選抜し、能力の傾きだけを変える（`ScoutModel.BuildCandidates` の `field` パラメータ）。候補に
「投手」「野手」のラベルは一切付けない（CLAUDE.md「守備位置・適性はゲームが提示しない」。
`PitcherRoleResolver.LeansPitcher` 等はスカウト側では一切参照しない）。

#### 年間の流れ
新チーム発足（夏の大会後）に、スカウトとの会話で①スカウト網の契約 → ②探す分野を決める（下の「スカウトの一年の入口」。
分野はリスト生成までなら画面の上部帯でも変更可・リスト生成時点の値で凍結） →
秋の大会後（第24週 `SeasonCalendar.RecruitListWeek`）に候補と寸評が届く → 冬に訪問で口説く →
3月（第46週 `SeasonCalendar.ProspectConfirmWeek`）に成否と入部が確定。既存の節目をそのまま使う
（新しい週は増やしていない）。

**操作が要る節目は強制イベント（issue #1035）。** 通知フィードの1行だけだと見落とし、その年は誰も口説かないまま
4月を迎える（契約の年額だけ払って何も得られない）。節目ごとにノベル（`data/events.yaml` の
`kind: System`・話者は `scout`）を出し、読み終えたらスカウト画面へ移る。**入口を除き、スカウト網が未契約（枠0）の年は
出さない**（入口は未契約の学校にも聞く）。 出すか・いつ出すかの判定は engine の `ScoutMilestones` に1箇所だけ置く。

| 節目 | 週 | イベント（`ScoutMilestones` の定数） | 出す条件 | 読み終えたあと |
|---|---|---|---|---|
| 一年の入口（契約→分野） | 新チーム発足の流れ（引退→主将指名→背番号決定）の終わった直後（第24週より前） | `scout_choose_field`（契約済み）／`scout_contract_offer`（未契約） | 今年ぶんの候補リストが未生成（**契約の有無は問わない**） | 会話の中で選んで終わる（画面は移らない）。詳細は下の「スカウトの一年の入口」 |
| 候補リストが届く | 第24週（`RecruitListWeek`） | `scout_list_arrived` | 枠あり・リストが出ている | スカウト画面の「スカウト」タブ。通知フィードの1行も残す |
| 締切前の念押し | 第44週（`ProspectConfirmWeek − 2`） | `scout_deadline` | 枠あり・成否未確定で、枠が余っている（`TargetedCount < Slots`）か、まだ誰も訪問していない | スカウト画面の「スカウト」タブ |

**スカウトの一年の入口（issue #1064・オーナー決定 2026-11-17）。** 会話の中で選択肢を出して決める（案C）。
選択肢は engine の `ScoutPitch` が持ち、会話文だけ `data/events.yaml`。監督には台詞を持たせない。
1. スカウト「今年もうちに任せてもらえます？」（未契約なら「契約しませんか」）→ **契約しない（0万）／Lv1（100万・枠2人）／
   Lv2（250万・枠3人）／Lv3（420万・枠4人）**。年額と枠数は選択肢に書く（カタログから引く）。選んだ瞬間に契約が確定する
2. 契約したら「どんな子を探しましょう」→ おまかせ／投球／打撃／守備走塁
3. 「10月にリストを持ってきます」で締め、結果行（太字）に「スカウト網 Lv2（年250万・枠3人）　探す分野: 投球」。
   **「契約しない」を選んだら 2・3 は出ない**（`scout_contract_declined` で締める。今年はリストなし）

- 読み終えてもスカウト画面へは移らない（入部済みの1年生の一覧が主役になる問題を避ける）。ホームへ戻る
- **経営タブのスカウト網は見るだけ**（いまの段と年額の表示。操作ボタン・解約なし）。年の途中で枠数や見立ての段が変わることは無い
  ＝リスト生成（第24週）の後に段を変えたときの扱いを決める必要が無くなった
- 夏〜第24週（`ScoutMilestones.AwaitingList`）に契約済みの学校が自分でスカウト画面を開くと、
  「スカウト」タブが開き、「候補リストは10月（第24週）に届く・探す分野: ○○」と出る
- **入部した子はスカウト画面に残さない**（2026-11-24 オーナー決定）。4月に年度が替わると、「入部予定者」タブは次の3月の確定まで
  空状態に戻り、「スカウト」タブも前年度の決着済みリストを出さない（3月の決着〜年度替わりのあいだだけ結果つきで見える）
- 会話を読み切らずに画面を離れたとき、決めていない分は前の状態のまま（契約は直前の段・分野はおまかせ）。
  待ちはセーブしない（スカウトの節目と同じ作法）ので、読み込み直すとその年の入口は出ない

念押しを第44週にしたのは、年契約の更新（確定週の直前＝第45〜46週）と同じ週に重ねないため。枠を使い切って
訪問も済んでいる年は出ない。分野を選べるかは「リストの有無」でなく**今年ぶん（合流年度＝今年度＋1）のリストの有無**で
決める（前年度のリストが残っていても、新しい年の分野は選べる）。

#### 入部の成否
進路希望は3種（候補1人に1つだけ割り当て）。**入部の見込み（%）は画面に出さない**
（オーナー決定・ワイヤー案A）。

- **名門志向**: 名声が高いほど来る（`scout.prob_per_fame`）
- **出場機会志向**: その子より強い部員が少ないほど来る（`ScoutModel.OpportunityScore`＝候補の最良4軸より
  弱い現ロスター部員の割合。`scout.prob_per_opportunity`）
- **地元志向**: 近いほど来る（`ScoutModel.Closeness`＝同県1.0〜遠方0.0。`scout.prob_per_local`）

距離の減点・競合校の格の減点・訪問の積み上げは進路希望に関わらず全員へ共通で効く（§2.2 の成功率モデルを
継承）。寮は距離の減点を6割打ち消す（`scout.dorm_distance_relief`）。競合校との争奪戦も残す
（訪問1回ごとに `scout.rival_event_prob`=0.22 で競合校の格が1段上がる）。

**進路希望の分布比・見立てノイズの具体値は issue 本文・オーナー決定に数値指定が無いため、無難な初期値
（等分・旧 §2.2 の値を踏襲）を置いた。バランス実測は未（issue #867 の『新入生の質の分布は専用の実測で』
を参照。統計帯はロスター生成を測らないため Heavy の安全網にならない）。**

#### 訪問の手応え（2026-11-24 オーナー決定）
入部の見込み（%）は出さないまま、訪問するたびに**その時点の成功率を4段の言葉へ丸めて返す**
（`VisitResponse`＝`ScoutModel.ResponseOf` / `UpdateResponse`。境目は `scout.response_*_min`＝0.25／0.45／0.65）。

| 段 | 成功率 | 文 |
|---|---|---|
| Eager | 0.65 以上 | 目を輝かせて聞いていた |
| Warm | 0.45 以上 | 悪くない反応だった |
| Lukewarm | 0.25 以上 | 反応は薄かった |
| Cold | 0.25 未満 | 心ここにあらずだった |

- 訪問直後の一言（「訪問した。○○。」）と、詳細カードの「手応え」の行（最後の訪問の段。未訪問は「—」）の両方に出す
- 式は3月の判定と同じ `SuccessProbability`。乱数もスカウト網の段のノイズも乗せない（監督が自分で会った感触）。
  争奪戦で競合校が動いた訪問は、動いた後の値で出す
- 3月までに名声・部員・競合校が動けば最終の成否とはずれうる（手応えは訪問した時点のもの）
- セーブは候補ごとの `response`。項目の無い旧セーブは未訪問扱いで読み、次の訪問で埋まる

#### 入部の条件（約束）（2026-11-24 オーナー決定）
訪問のとき、候補が**入部の条件**を出してくることがある。約束すれば口説きやすくなり、入部後に破ると信頼度と名声が下がる。
冬のスカウトが翌年以降の采配に効いてくる仕組み。

**実装の進み具合**: 第1段＝条件を出す・約束する・本人に持たせる・セーブ（実装済み）。
第2段＝公式戦での判定・信頼度と名声の増減・通知フィード・スタメン設定と交代画面で思い出させる仕組み（実装済み）。
第3段＝采配の委任・裏解決の AI に約束を守らせる（実装済み）。

**AI に約束を守らせる（第3段）**
- 自校の公式戦のチームに「約束の見張り」（`Team.PromiseGuard`＝`MatchPromiseGuard`。代打禁止・バント禁止・途中出場禁止・
  登板禁止の選手ID）を載せる（`ScoutPromiseJudge.GuardFor`。物差しは試合後の判定と同じ）。見張る約束が無ければ null
- エンジンは采配AIの判断を適用する前に見張りで除外する（判断そのもの＝乱数の消費は変えない）。代打・代走・守備固めの候補から
  約束の子を外し、約束の打者への代打・バント・スクイズ（打席頭のサインも1球ごとの指示も）は採らない
- 継投は約束の子を飛ばして名簿順で控えを選び、控えに投げられる子がいなければ守っている野手をマウンドへ回す
  （**オーナー決定 2026-11-24「野手を投手に回してでも約束を守る」**。野手は制球＋球速の高い順。控えから守備を補充せず、
  現投手がその守備位置へ回る）。球数制限で継投が強制されたときも同じ
- プレイヤーが手で行う交代・サインは見張りを通らない（画面の警告と二度押しで守る）。AI校・裏試合・統計シムは見張り無し＝従来どおり
- 自動スタメンは対象外: 公式戦は毎回スタメン設定画面を通り、プレイヤーが確定する（警告と二度押しが効く）

**判定の節目（`ScoutPromiseJudge`・乱数なしの純ロジック）**

| 節目 | 決着する約束 |
|---|---|
| 公式戦1試合の後（`AfterOfficialGame`） | 破り＝レギュラー・4番・上位打線（スタメンの打順で見る。怪我の子は数えない）・1年夏は出さない（夏に出場）・代打を出さない（スタメンで出て代打を送られた）・バントさせない（犠打が記録された＝成功した送りバント・スクイズ。2026-11-24 オーナー決定）・連投させない（同じ大会の前日にも登板）。果たした＝1年から出場（途中出場でよい）・先発で投げたい（先発した）・1年夏は出さない（秋の大会が来た） |
| 年度替わりの直前（`AtYearEnd`） | 1年目だけの約束で破らなかったもの＝守り切った。1年から出場・先発で投げたいを果たせていなければ破り。卒業する3年の生きている約束＝守り切った |
| 4月の入部（`AtJoin`） | 寮（その時点で寮があるか） |
| 新チームの背番号決定（`AfterNumbersDecided`） | 一桁の背番号（1年の秋） |
| 新チームの主将指名（`AfterCaptainNamed`） | 主将（本人が2年の秋） |

- 1年目の起用の約束（レギュラー・4番・上位打線・代打・バント）が見るのは夏と秋の大会（県大会・秋季地区予選・地区大会）だけ。センバツ・神宮は数えない
- 連投は「同じ年度・同じ大会の中で前日も登板」（`PitchDayStamp`。大会をまたぐと連続しない）。最後に登板した日は全員ぶん `DevelopingPlayer.LastOfficialPitchStamp` に残す
- 信頼度・名声の増減と通知フィードは Shell の `ScoutPromiseTracker`（公式戦の後は「本日」、週送り・年度替わりは「今週」の通知に流す）

**思い出させる仕組み（実装済み）**
- 約束が生きている選手には、スタメン設定（打順の行・先発投手カード・控え）と交代画面（打順表・控え）の名前の横に、条件の短い名前のタグ（`UiComponents.PromiseTag`）が付く
- いまの並び・保留中の交代で約束を破るなら、そのタグが警告色になり、警告行（スタメン設定）・注記（交代画面）に「約束を破る：名前（条件）」を出す。判定は試合後と同じ物差し（`WouldBreak` / `BreaksOnEntry` / `BreaksWhenPinchHitFor`）。公式戦のときだけ
- 破る状態で決定・確定するときだけ、1回目はボタンの文が「約束を破って決定／確定」に変わり、もう一度押すと通る（並び・操作が変わったら押し直し）

**骨格（オーナー決定）**
- **たまにしか出ない**。候補1人につき最大1回、訪問1回あたり `scout.promise_ask_prob`（0.15）で出る。
  **約束すれば成功率が上がる**（`promise_bonus` 0.18＝訪問2回ぶん）。断っても成功率は下げない（条件が出ること自体を損にしない）
- **実力に見合う条件だけ**が出る。本人の本当の能力を自校の部員の中での順位で見る
  （4番確約＝打撃で部内2位まで／上位打線・バントさせない＝5位まで／レギュラー確約・一桁の背番号・代打を出さない＝9位まで／
  1年から出場＝18位まで／1年夏は出さない＝10位以下／先発＝投球がいちばん強い軸で投手力3位まで／連投させない＝同5位まで／
  主将＝統率傾向70以上／寮＝県外の子で寮が無いとき）。投手系の条件に `PitcherRoleResolver` の投手判定は使わない
- **進路希望と矛盾しない**。合う条件は重み3・関係ない条件は重み1・矛盾する条件は出さない
  （出場機会志向は起用系が合い「1年夏は出さない」は出さない／名門志向は「1年夏は出さない・連投させない・寮・主将」が合う／
  地元志向は寮を出さない）
- 出たら、スカウトとの会話の中で「約束する／約束はできない」を選ぶ（会話は `data/events.yaml` の `scout_promise_*`）。
  返事をするとその場で手応えを取り直す。読み切らずに離れたら約束しなかった扱い
- 約束した子が入部すると、約束は本人が持つ（`DevelopingPlayer.Promise` / `PromiseStatus`）
- 判定は**公式戦だけ**（練習試合は数えない）。条件ごとに期限を持つ。怪我で出られない試合は破りに数えない
- 破った時点で信頼度 −5・名声 −5 を**1回だけ**下げ、その約束は終わる（毎試合は下げない）。
  守り切ったら信頼度 +2（`promise_broken_trust` / `promise_broken_fame` / `promise_kept_trust`）
- 采配の委任・高速試合・自動スタメンの AI は約束を守って組む（プレイヤーのせいでない破りを作らない）
- 排他的な約束（4番確約・主将）は、すでに誰かとしていれば出さない
- 進路希望と連動する（出場機会志向は起用系を出しやすい）
- 守備位置の希望（「ショートで使って」等）は作らない＝ゲームが適性を教えることになる

**条件の一覧**

| 条件 | 破りの判定 | 期限 |
|---|---|---|
| レギュラー確約 | 公式戦でスタメンから外れた | 1年秋の大会まで |
| 1年から試合に出してほしい | 期限内の公式戦に一度も出場しなかった（途中出場でよい） | 1年のうち（3月の年度末で決着） |
| 4番確約 | 公式戦のスタメンで4番以外 | 1年秋の大会まで |
| 上位打線（1〜5番）で | 公式戦のスタメンで6番以降 | 1年秋の大会まで |
| 1年夏は出さないで（体づくり） | 1年夏の公式戦に出場した | 1年夏 |
| 代打を出さないで | スタメンで出た公式戦で代打を送られた | 1年秋の大会まで |
| バントさせないで（打たせて） | 公式戦の打席でバント・スクイズのサインを出した | 1年秋の大会まで |
| 連投させないで | 公式戦で2日続けて登板した | 在学中 |
| 先発で投げたい | 期限内の公式戦で先発登板が0回 | 1年のうち（3月の年度末で決着） |
| 一桁の背番号がほしい | 1年秋の背番号決定で10番以降 | 1年秋 |
| 主将にしてほしい | 2年秋の新チームで主将に指名しなかった | 2年秋 |
| 寮に入りたい | 4月の入部時に寮が無い | 入部時 |

- **入れない**: 「甲子園に連れて行って」（オーナー判断で不採用）／「球数100球以内」（試合中に1球ずつ見張ることになり手間。
  健康面は「連投させないで」で代える）
- **後回し**: 「友達も一緒に」（候補リストの作り方から変わる）
- **将来**: 約束を守る・破るが**中学チームとの関係**に響く（次の年以降の候補の来やすさ）。中学チームという単位は未設計

**思い出させる仕組み（オーナー決定）**: 約束のある選手に共通の印／破る配置の行は警告色／
破る状態でオーダーを確定・交代するときだけ確認／選手詳細に内容と期限／破った・守り切ったときに通知フィード。説明文は足さない。
実装の中身は上の「思い出させる仕組み（実装済み）」。選手詳細は見出しの学年・投打の並びに同じタグで
「条件・期限」（決着後は「条件（守った／破った）」）を出す（`ScoutPromises.DetailText` / `DeadlineLabel`）。

## 3. イベントテーブル（データ駆動）

### 3.1 定義フォーマット（YAML → C#へロード）
```yaml
- id: skipping_practice
  kind: Choice
  scene: ground          # ノベル画面の背景になる場所（issue #1516・表示専用）
  weight: 1.0
  cooldown_weeks: 12
  text: "主力が練習をサボっているらしい。"
  variants:
    - lines:
        - who: team_manager
          say: "監督、{player} くんがまた練習の途中で消えました。今週3回目です。"
  choices:
    - stance: scold
      label: "呼び出して、きっちり叱る"
    - stance: listen
      label: "まずはサボる理由を聞いてみる"
  outcomes:
    - stance: scold
      result: improved
      lines:
        - who: narration
          say: "翌朝、{player} は誰よりも早くグラウンドにいた。"
```
（正典は `data/events.yaml`。上は抜粋。旧版の例だった「エースの違和感」`ace_hidden_injury` は
選択肢も効果も無いまま出ていたのでイベントごと削除した＝2026-11-23 作らないと決定・#1477）
- Claude Codeでの量産・追加・バランス調整をデータ編集だけで完結させるための構造
- `scene:` はノベル画面の背景を選ぶ場所（issue #1516）。ground グラウンド／bench 球場／school 教室／clubroom 部室／
  office 監督室／camp 合宿所／hall 体育館／night 夜のグラウンド の8つ。**全イベントに明示**する（省略はグラウンドに落ちるが、
  背景の考え忘れを防ぐため正典では書く＝`EventTableTests.RepositoryTable_EveryEventDeclaresScene`）。未知の語はパーサが例外にする。
  発火・効果には一切使わない
- **OBの居ない学校ではOBが出てくる話を出さない**（issue #1615）。OB＝その学校の野球部の卒業生。転任で引き継いだ学校（もともとAI校）は
  歴史があるので常に居る。新設校は卒業生が1人以上出る（最初の卒業は3年目の年度末）まで居ない
  （`RosterService.HasOb`＝「新設校として始まったか」`SaveState.SchoolFoundedNew`＋卒業生の数。セーブは版を上げず、キーが無い旧セーブは居る扱い）。
  データには2つの印を書く: イベント直下の `requires_ob: true`＝OB会の寄付のようにイベントごと抽選から外す（`EventScheduler.ObFilter`）／
  variants の要素の `requires_ob: true`＝イベントは残し、OBに触れる会話だけ候補から外す（`EventScheduler.PickScript` の `hasOb`）。
  フィード1行がOBを名指しするイベントは `text_no_ob:` に居ない学校の文を書く（`GameEvent.TextFor`）。
  OBが居る学校の抽選は従来と1語も変わらない（候補が減らない）。`ObFilter` が null（名簿を持たないヘッドレスシム）は判定しない＝帯不変

### 3.2 フラグ管理
- グローバルフラグ（キャリア通算） / 年次リセットフラグ / 選手個別フラグ の3層
- 発生制御: 同一週最大1件、同一イベントにクールダウン、重み付き抽選

### 3.3 初期ラインナップ（抜粋20件）
- 固定: 入学式、仮入部→正式入部、テスト週×4、夏合宿、冬合宿、文化祭、ドラフト会議、
  プロ入りOBの挨拶訪問（元祖踏襲）、卒業式、転任辞令（3月・判定連動）
- ランダム: 怪我、雨天週、取材、プロスカウト視察、OB寄付、感染症で部活動停止
- 選択肢: 練習サボり、無名1年の自主練、保護者からの起用クレーム、
  部員間の不和、他校からの引き抜き噂（フリー化後）

### 3.4 赴任イベントとチュートリアル（issue #1496・2026-11-23 ユーザー決定）

マネージャー（§1.3a）が主体で、①監督を迎える**赴任イベント**、②進め方を教える**チュートリアル**を出す。
会話はどちらも data/events.yaml の `kind: System`（話すのは `who: team_manager`。監督は聞き役）。
何をいつ積むかは engine の `Tutorial`（`KokoSim.Engine.Career`）が1箇所で決め、Unity は返った id を積むだけ。乱数不使用
（言い回しの選択だけ `EventService.Rng` の専用の用途から引く）＝試合結果の指紋に影響しない。

- **赴任イベント**: 「はじめから」で新設校を作った直後（`arrival_new_school`・1年のマネージャー「監督！お待ちしていましたよ！」）と、
  転任を確定した直後（`arrival_transfer`・転任先の2年か3年のマネージャー「お噂はかねがね…」）。残留では出さない
  - `arrival_new_school` は3通りどれを引いても、**部員は1年生だけ**（新設校なので先輩がいない）と、**監督は教員として赴任した**
    （雇われの外部監督ではなく、先生として来て野球部を任された。§1.3 の教員監督・転任の出発点）が伝わるように書く。
    呼び方は「先生」と「監督」を混ぜてよい。監督（`who: manager`）は喋らず、ナレーションとマネージャーが語る（イベント会話の作法）
- **チュートリアル**: 「はじめから」の進行だけ（転任は赴任イベントだけで、説明を積まない）。場面ごとに分け、その場面が**初めて**来たときに1回だけ出す

| 場面（`TutorialScene`） | いつ | 教えること |
|---|---|---|
| Basics | 赴任イベントの直後 | 「今週を進める」で週が進む／練習メニューの決め方 |
| FirstTournament | 初めての公式戦の開幕（開幕の演出が消えた後） | 大会の流れ・ベンチ入り（背番号）とスタメン |
| FirstMatch | 公式戦・練習試合を問わず最初の1試合の前（公式戦は試合の日の開始確認の前、練習試合は申し込み成立後・スタメン設定の前にホームで。試合の画面ではノベルを出さない。2026-11-23 オーナー決定） | サイン・タイム（伝令・選手交代）・委任 |
| Scouting | 初めてのスカウトの時期（新チーム発足後・契約の会話の前） | スカウトと新入生 |
| Purchases | 週送りの後、部費で施設・道具・備品のどれかの次の段が買えるとき（初回） | 部費と施設・道具 |
| SummerRetirement | 初めての夏の引退（引退の会話の後・主将指名の前） | 3年の引退と新チーム・主将 |

- **スキップ**: 赴任イベントとチュートリアルの会話は「スキップ」で最後の行まで飛ばせる。チュートリアルは最後に
  「分かった／もう説明はいらない」の2択を出し、「もう説明はいらない」を選ぶと残りの説明もまとめて出なくなる（`tutorial_dismissed` の返事が続く）
- **セーブ**: 見た場面の集合と「もう説明はいらない」を v42 で載せる。v41 以前のセーブは「全部見た扱い（もう説明はいらない）」で補う
  ＝途中から遊んでいる人に急に説明を出さない
- 見た印は**積んだ時点**で付ける（イベントの場面が残っている間はセーブできない＝積んだのに見ていない状態は保存されない）
