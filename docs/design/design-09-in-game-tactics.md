# 設計書09: 試合采配システム（サイン・守備指示・伝令）

試合中の監督の介入を**3層**に整理する。
現実の野球と同じく「サインは無制限、伝令は回数制限」の構造を採る。

| 層 | 頻度 | 内容 |
|---|---|---|
| サイン | 1球ごと・無制限 | バント、盗塁などの作戦指示 |
| 方針 | 常時設定・随時変更 | 配球方針、守備陣形、走塁積極度 |
| 伝令 | **攻撃・守備 各3回/試合** | 精神面への介入（現実の高校野球ルール準拠） |

---

## 1. 攻撃サイン（1球ごと、詳細モードの作戦パネル）

| サイン | 効果 | リスク |
|---|---|---|
| 強攻 | 通常打撃 | — |
| 待て | 1球見送り（四球狙い・球数稼ぎ） | ストライクを取られる |
| 送りバント | 設計書02 §4.3の解決式 | 小フライ併殺、失敗 |
| セーフティバント | 走力依存の内野安打狙い | 同上 |
| スクイズ | 設計書02 §4.4 | ウエストで挟殺の大惨事 |
| 盗塁 | 設計書02 §4.2 | 盗塁死 |
| エンドラン | 走者スタート＋打者は必ず当てにいく（ミート補正↑・パワー補正↓、ゴロ性向↑） | 空振り→走者憤死、ライナー併殺 |
| バスター | バント構えから強攻（相手バントシフト時に有効） | 準備不足の打撃補正↓ |

- サインの成否には**相手バッテリーの読み**が絡む（捕手リード＋投手センス vs 状況の意外性）。
  読まれた場合はウエスト・ピッチアウトで対抗される

### 1.1 打撃姿勢（2026-07-31・采配カードの拡充）

サインが「この打席で何をするか」なのに対し、**打撃姿勢は「どう打ちにいくか」＝解除するまで続く構え**。
打席頭に一度だけ効き、打席内では変わらない（`BattingApproach`）。

| 姿勢 | 効果 |
|---|---|
| 待球策 | スイング頻度↓（球数を投げさせる。能力は動かさない） |
| 転がせ | 弾道↓・ミート↑・パワー↓ |
| 長打狙い | パワー↑・弾道↑・ミート↓ |
| 当てに行け | ミート↑・パワー↓（弾道は動かさない） |

- 効果は**実効能力への倍率**と**スイング頻度の倍率**の2つにしか落ちない。確率へ直接触らず、
  表示能力→物理層の変換の前段で能力を動かすだけ（不変条件#1）。エンドランとまったく同じ流儀
- 既定（指示なし）は恒等で、乱数を1発も引かない。**AI校は使わない**ので統計帯・digest は不変
- 係数は `data/coefficients.yaml` の `tactics:` 節（`work_count_swing_factor` 等）

### 1.2 プレイヤーの采配窓口（`MatchProgression`）

寿命が2種類ある。エンジンの既存モデル（守備指示＝常時設定 / 1球指示＝使い捨て）にそのまま重ねている。

| 窓口 | 寿命 | 何が載るか |
|---|---|---|
| `SetPitchBattingOverride` | 1球 | 積極的に / 待て / バント / スクイズ |
| `SetOffensiveSign` | 1打席 | エンドラン（＝走者スタート＋打撃補正） |
| `SetStealAttempt` | 1球 | 盗塁（始動種別・狙う塁） |
| `SetBattingApproach` | 解除まで | 打撃姿勢（上表） |
| `SetStandingDefense` | 解除まで | 配球方針 / ギア / 内野・外野の深さ |

- 適用は**brain 呼び出しの後**に置く。こうすると指示の有無で brain のRNG消費が変わらず、
  同シードの乱数順が保たれる（指示なしなら読み取りだけでRNG非消費）
- 4窓口とも `GameDecision` へ記録し、中断保存→復元で再現する

## 2. 守備指示

### 2.1 守備陣形（元祖のボタン構成を踏襲）
- **内野**: 前進 / 普通 / 後退（バックホーム態勢 ⇔ 併殺・長打警戒）
- **外野**: 前進 / 普通 / 後退（浅い打球ケア ⇔ 頭上を抜かれない）
- 現代化で追加: バントシフト（一・三塁手チャージ、二遊間がベースカバー回転 → 設計書01の守備陣形ルール表の初期配置を差し替え）
- 陣形は守備解決（幾何計算）の**初期守備位置そのもの**なので、効果は自然に物理から出る:
  前進守備はゴロの本塁封殺率が上がる代わりに、間を抜かれると長打になる

### 2.2 配球方針（自動配球への重み付け）
| 方針 | 配球AIへの影響 |
|---|---|
| おまかせ | 捕手リード＋投手センスの素の判断 |
| 直球中心 | ストレート比率↑（押せる投手向け） |
| 変化球中心 | 変化球比率↑（球威で劣る時） |
| コントロール重視 | ゾーン内比率↑・四球回避（球数も節約） |
| 低め徹底 | 低目比率↑・長打抑制、暴投リスク微増 |
| 強気の内角 | 内角比率↑・打者の踏み込み抑制、死球リスク増 |

- 詳細モードの1球指示は方針より常に優先（方針は「指示しない球」に効く）
- ウエスト / 申告敬遠は独立コマンド（元祖踏襲）

### 2.3 守備位置の入替（コンバート）

出場中の選手どうしで守備位置だけを交換する操作（issue #235）。**選手の出入りが無いので野球ルール上「交代」ではなく、
回数無制限・審判告知のみ**。したがって:

- **交代回数（`TeamState.Substitutions`）を消費しない**。リエントリー禁止にも抵触しない（誰も退場しない）
- ただしリプレイ再現のため決定列（`GameDecisionKind.SwapDefense`）へは積む（不変条件#2）
- 交換なので9守備位置の一意性は自動で保たれる。規則は engine の `DefenseAssignment`（試合前のスタメン設定と共通）
- 投手スロット・DHスロットは対象外。投手が守備位置を動くのは「登板の変更」なので §6 の投野交代／コンバート継投で扱う
- UI: 守備中の交代モーダル「守備の割当」2ペイン（§6・issue #256）。在フィールド同士の枠を2つクリック＝入替。
  `TeamState.SwapDefensivePositions`（`IsSwappableDefenseSlot` で投手・DH枠を除く）は AI の守備位置操作（§2.3 の敵AI継続）と共有する純データ規則で、プレイヤーUIもこの枠集合を「入替できる守備」として使う

## 3. 伝令（攻撃・守備 各3回/試合）

- 回数: **攻守それぞれ1試合3回まで**。延長では1イニングにつき1回追加（現実ルール準拠）
- 効果はすべて**精神系**（設計書02 §3のプレッシャー指数まわりに作用）:

| 種類 | 効果 |
|---|---|
| 守備伝令（マウンドへ） | 投手の「動揺」状態を解除。プレッシャー指数の負補正を数打席の間緩和。連打時の立て直し |
| 攻撃伝令（打者・走者へ） | 打者の緊張緩和（精神力の負補正を一時中和）。走者への確認（暴走系の判断ミス率↓） |

- 効果量は監督の采配能力と選手の性格で変動
- 「ここで使うか、9回に取っておくか」という資源管理が采配の華になる設計

## 4. 高速モードとの関係

- 方針（配球・陣形・走塁積極度）は高速モードでも常時有効
- サインはAI代行（監督の采配能力で質が変わる）
- 伝令は高速モード中でも任意のタイミングで一時停止して使用可能

> **観戦ライブの停止粒度はこの高速モード像に一本化した（issue #173・2026-07-24）。**
> 試合ライブ観戦は「打席ごとに手動で進める」を廃し、終局まで**連続自動進行**する。プレイヤーは
> **任意のタイミングで「タイム」をかけて中断**し、采配一式（交代・サイン方針・伝令効果）を差し込んで再開する。
> ~~「タイム」は**有限資源＝伝令**（§3・攻守各3回・延長で毎回+1）を消費する。~~攻守どちらの伝令かは
> その場面の表裏×自校の先後（攻撃中＝攻撃伝令／守備中＝守備伝令）で自動判定し、~~残数を常時表示~~、残0では不可。
> これは design-15 §0 の「停止粒度＝打席頭のみ＋手動一時停止」を上書きする決定である。

> **中断と伝令消費を分離した（issue #289・2026-07-28。上の取り消し線部分を上書き）。**
> 中断の入口は「タイム」ボタンではなく**試合画面の任意クリック**になり、クリック中断は演出を止めるだけで
> **伝令を消費しない**（エンジンに触れない）。伝令は中断ポップアップ内の「伝令を送る」で明示的に1回消費する
> （1中断につき1回・攻守自動判定・残0では不可は従来どおり）。**選手交代も伝令とは独立**になり、中断中なら
> 伝令を使わずに実行できる。伝令残数の常時表示は廃止し、ポップアップ内のボタンにだけ残数を出す。
> いずれも表示・操作導線の変更のみで、エンジンの決定論経路（`CallTimeout` / 交代API）は不変＝帯・digest不変。

## 6. 指名打者（DH）

- ラインナップ構成の切替として実装。打席解決パイプライン（設計書01 §2）は変更しない
- DH有効時: 打順9人のうち1枠が**守備位置を持たない打撃専門（DH）**、投手は打順外
- DH解除の分岐（現実ルール準拠、監督采配として発生）:
  - DHの選手を守備に就かせる → 以降そのゲームはDH消滅（投手が打席へ）
  - 投手をそのまま打席に立たせる交代 等
- 育成・スカウトへの波及: 「守備は難があるが打力が図抜けた選手」の居場所が生まれる。
  弾道・パワー特化型の価値が上がり、起用の幅が広がる
- 設定トグル（設計書05 §1.3）。年代連動で導入年以降は自動ON

### 6.1 守備交代で入る選手の守備位置（任意割当）

守備交代は既定では**退く選手の守備位置を継承**する（1対1）。加えて、入る選手を**任意の守備位置**に就かせられる
（issue #235）。押し出された既存野手が空いた位置へ回る＝守備位置シャッフル。
実装は「守備交代（1回消費）→ §2.3 の入替（無料）」の合成なので、消費する交代回数は1回のまま。

### 6.2 コンバート継投（投手→野手＋控え投手の登板）

投手を外野等へ回して控え投手を継投させる采配（issue #235）。**元投手は退場していない**ので:

- 打席に立ち続け、**後で再登板もできる**（リエントリー禁止は「退場した選手」にのみ適用される）
- 球数・スティント疲労は**選手単位で持ち回す**。コンバートを挟んでスタミナが回復する抜け道は作らない
- 退場するのは押し出された野手（その打順スロットへ新投手が入る）。非DHでは元投手が自分の打順スロットに残り、
  DH制では元投手が押し出された野手の打順スロットを引き継ぐ（DHは維持）
- engine: `TeamState.ConvertPitcherAndRelieve` ／ 決定列は `GameDecisionKind.ConvertRelief`
- 在フィールド野手をマウンドへ上げる**投野交代**（issue #209）は別コマンド（`RelieveWith`）。
  こちらは「野手が上がって旧投手が空き守備へ回る」＝向きが逆

### 6.3 守備側の交代UI＝「守備の割当」（issue #256）

守備中の交代は**1操作＝「誰を・どの守備に割り当てるか」**に統合した（旧・投手交代／守備交代／守備位置／DH解除の4タブを廃止）。
スタメン設定（試合前・#233）と同じ**割当2ペイン**で、規則は同じ `Season.DefenseAssignment`（守備位置の一意性・投/指も1枠として動く・#93）に一本化する。

- **左＝守備の割当10枠**（投・捕・一・二・三・遊・左・中・右・指）。**右＝控え一覧**（役割で分けずフラット・背番号順・出場済みは灰）。
- **枠→枠**＝入替（可逆・誰も退場しない）。**枠→控え**＝投入（不可逆・退場が出る）。結果は操作から導出する:

| 操作 | 導出される交代 | engine 受け口 |
|---|---|---|
| 控え → 投枠 | 継投 | `MatchProgression.Relieve`（→`RelieveWith`→`ChangePitcherTo`） |
| 在フィールド野手枠 ⇄ 投枠 | 投野交代（2人をそのまま入れ替え） | `MatchProgression.SwapPitcherWithFielder`（→`PromoteFielderToMound` の①固定） |
| 控え → 守備位置枠 | 守備固め／守備割当 | `MatchProgression.DefenseAssign`（→`AssignFielderToSlot`） |
| 在フィールド ⇄ 在フィールド | 守備位置の入替 | `MatchProgression.SwapDefensivePositions` |
| 投枠 → 控え投入＋元投手を守備位置へ | コンバート継投 | `MatchProgression.ConvertPitcherAndRelieve` |
| 指枠 ⇄ 守備位置枠 ／ 指枠を退場 | DH解除 | `MatchProgression.ReleaseDh(pos / null)` |

- **継投候補はプレイヤーもAIも同一集合** `TeamState.ReliefRankingCandidates`（ブルペン＋ベンチ＋在フィールドの守備野手）を通る
  （`SubstitutionOptions.ReliefCandidates`）。在フィールド野手を指名すると投野交代になる（§6.2 と向きが逆）。
- **投野交代の空き守備は、プレイヤー操作では必ず旧投手が埋める**＝単純な入れ替え（issue #452）。
  `RelieveWith(..., allowBenchBackfill: false)` で②（旧投手退場＋ベンチ野手で補充）へ倒さない。
  ②は AI が「継投したい」とだけ決めたときの穴の埋め方であって、**打順表で2枠を指す明示操作の意味ではない**
  ＝画面のプレビューと確定結果が食い違わない。AI の継投（`Relieve`）は従来どおり①/②を判定する＝帯不変。
  DH制だけは投手が打順外で入れ替えが成立しないので、**元DHが空き守備に就いて投手は退場**（DH解除）に倒れる。
- 継投は最頻操作なので、守備中にモーダルを開くと**[投]枠をプリセレクト**する（控えを1クリック→確定で従来と同手数）。
- **打順表の窓は10行ぶん取る**（`.msub-scroll` 460px＝行間ピッチ46px×10）。DH制では打順9人に加えて
  打順外の投手が1行増え、issue #452 で並びを打順順にしたためその投手行は末尾に来る。9行ぶん（414px・issue #254）
  のままだと**DH制のときだけ、継投で真っ先に押す[投]枠が窓の外に落ちて見えない**（2026-08-10 実測）。
  この列は隣の比較列（578px）に合わせて590pxへ引き伸ばされており、打順表は463pxしか使っていない
  ＝10行にしてもモーダルは伸びない。
- 可逆（入替）と不可逆（投入・DH解除＝退場）が同居するので、**確定前に「この操作で誰が退場するか」をフッタに必ず出す**。
- 決定列は `GameDecisionKind.Relieve` / `SwapPitcherWithFielder` / `DefenseAssign`（他は従来どおり）。全経路が添字ベースで Save/Load・委任AI再生と決定論一致（不変条件#2）。
- AI の継投・守備位置操作（`GameEngine`）は従来の `RelieveWith` / `SwapDefensivePositions` 経路のまま＝統計帯は不変（issue #256 はプレイヤーUIの統合）。

## 7. タイブレーク

- 延長は**無死一・二塁＋前イニングからの継続打順**で開始（現実の高校野球ルール準拠）
- 開始イニングはトグルで設定可能（規定回から / 延長即時 など、年度で変わるためデータ化）
- エンジンは走者配置と打順を初期化してイニングを回すだけ。既存の試合エンジンで完結
- 采配への影響: タイブレークでは送りバント・スクイズ（設計書09 §1）の価値が跳ね上がる。
  伝令の残回数（§3）をここまで温存したかどうかが勝負を分ける設計
- 設定トグル（設計書05 §1.3）。年代連動
- **タイブレークOFF／導入前年代での延長上限（15回）同点の決着**: トーナメントでは**引き分け再試合**で
  決着させる（別Fork の再試合、上限後は安打数→強さ→ID の規定決着）。仕様と決定論の詳細は**設計書05 §1.3**
  「引き分け再試合」（issue #253）を正典とする。タイブレーク有効時は15回同点自体が激減するが、この経路は
  タイブレーク配線と独立に成立する。

## 8. 主将（キャプテン）

チームに1名指名。**実力ではなく統率力（性格・精神力ベース）で選ぶ**のが本来の姿で、
「実力は劣るが精神的支柱の主将を、無理にスタメンで使うか？」という采配ジレンマを核にする。

### 8.1 効果
- **試合中（在場時）**: 主将がグラウンドに立っている間、チーム全体の**プレッシャー指数の負補正を緩和**
  （設計書02 §3。緩和量は主将の統率力＝性格×精神力に比例）。ベンチにいる間は効果が大きく減衰
- **チーム運営**: 士気・結束にボーナス。設計書03の選択肢イベント（不和・サボり等）の好転率が上がる
- **育成**: 主将本人の精神力・実戦系能力の成長がやや促進（重責が人を育てる）

### 8.2 起用ジレンマ（設計の主眼）
- スタメン起用: 打線の総合力は下がるが、試合を通して全体が締まる（終盤の失点・凡走を抑える）
- ベンチ/代打起用: 打線は最強で組めるが、接戦終盤にチームが浮き足立ちやすい
- 統率力の高い主将ほどこの天秤が重くなる → 「無理にでも使うか」の悩みが毎試合発生
- 主将が不在（ベンチ外・故障）だと運営・試合の両ボーナスを失う → 主将の代えの育成も課題に

- エンジン接続: プレッシャー指数の補正項に「主将在場フラグ×統率力」を加算
