# Steam 発売ロードマップ（体験版つき）— 2026-11-19 策定

## Context

KoKoSimNext を Steam で販売したい。その前に体験版を出す。あわせて「推奨スペックをどうするか」「重くないか」を決めたい。

**現状**（2026-11-19 の調査）
- ゲームとしての 1.0 範囲はほぼ揃っている。ship-blocker の残りは #1085 の1件だけ。ラベルの無い issue が5件ある。
- 製品として出す下地がまだ無い。
  - 社名は DefaultCompany のまま。アイコン、ビルドスクリプト、設定画面、クレジット画面、チュートリアル、Steamworks 連携も無い。
- **製品ビルドで重さを測ったことが一度も無い。** fps・メモリ・待ち時間はどれも未計測で、手元にある数字はすべてエディタか CLI のもの。

**決まったこと**（ユーザー回答）
| 項目 | 決定 |
|---|---|
| 対応OS | Windows のみ。Mac・Steam Deck は発売後に検討 |
| 体験版の範囲 | **2年目の夏が終わるまで**。1年目から見てきた選手の最後の夏は遊ばせない |
| 体験版の配り方 | Steam の体験版（ダウンロード版）と、**ブラウザで遊べる版**の両方 |
| 発売時期 | 決めない（完成次第）。段階の順番だけ決める |
| タイトル | 新しいタイトルを付けて商標を調べる |
| 実在の名前 | 甲子園・センバツ・球場名は1か所に集めて差し替えられるようにし、調べた結果で実名にするか架空名にするかを決める |

## 「重くないか？」— 今の見立て

| 観点 | 見立て | 根拠 |
|---|---|---|
| 絵（GPU） | **中くらい**。最近の内蔵GPUなら軽量設定で動く見込み（未計測） | 甲子園の球場は約37万ポリゴン（うち観客25万）。守備場面では最大約15人がアニメで動く。SSAO・柔らかい影（4段カスケード）・ブルームを使っている。インスタンシングも LOD も無い。対決の絵は 960×540 に描いて拡大している |
| 計算（CPU） | **大会日の待ち時間が一番の弱点**。コア数で速さが変わる | 裏試合は `min(3, コア数−2)` 本で並列に回している（4コアなら2本）。地元県の1回戦の先読みは、1本で 8.3秒、並列で 2.0秒（エディタ実測）。年度替わりに数秒止まると記録されている |
| メモリ | **8GB 機で動くかが要確認** | 全国 4,000 校・約13万人を抱えている。エディタ全体で約2GB。製品ビルドの値は不明 |
| 容量 | **約1GB の見込み** | 球場メッシュが7個で約200MB。フォントのアトラスが 34.5MB×6。音声は wav 1,303本 |
| 良い材料 | エディタで感じるより軽くなる可能性が高い | エディタの Mono はデバッガ付きで遅い。CLI 比で27倍遅いという記録がある |

### 推奨スペック（仮。計測して確定する）
| | 最低 | 推奨 |
|---|---|---|
| OS | Windows 10 64bit | Windows 10/11 64bit |
| CPU | 4コア（Core i5-7400 / Ryzen 3 1200 相当） | 6コア以上（Core i5-9400 / Ryzen 5 3600 相当） |
| メモリ | 8GB | 16GB |
| GPU | Intel UHD 620 相当（軽量設定・1280×720） | GTX 1050 Ti / RX 570 相当（1920×1080） |
| API・容量 | DirectX 11・3GB | DirectX 11・3GB（SSD） |

**決め方**：最低スペック相当の Windows 機（4コア・8GB・内蔵GPUのノート）と、普通の機（6コア・16GB・単体GPU）の2台で測る。合格の線は次のとおり。
- 最低機：試合の3Dで 30fps 以上、大会日の待ちが ○秒以内、3年遊んでも落ちない
- 推奨機：60fps
- 線を超えたら、軽量設定を足す（SSAO を切る・影を減らす・観客を間引く・描画解像度を下げる）か、表記を上げる

## 段階（順番だけ決め、日付は置かない）

### 段階0：決めること・申し込み（すぐ始める。待ち時間が長いもの）
- 新しいタイトルの案を出す → J-PlatPat と Steam で同名・類似を調べる → 確定する
  - 確定するまで段階1の社名・製品名を固定できない
- Steamworks に登録する：1作 $100（売上 $1,000 で返金）、本人確認、税務インタビュー（日米租税条約）、口座登録
  - 支払いから30日たたないと発売できないので、早めに済ませる
- Windows の検証機を用意する（最低スペック機を兼ねる）
- 公開リポジトリをどうするか決める（下の「決めること」）

### 段階1：Windows の製品ビルドを作り、重さを測る
- `companyName` と `productName` を確定値にする
  - セーブの置き場所（`persistentDataPath`）はこの2つで決まる。**最初の公開ビルドより前に固定し、以後は変えない**
  - 体験版と製品版を同じ値にすれば、セーブは自動で同じ場所に入る＝引き継ぎが楽になる
- ビルドスクリプトを作る（Editor メニュー＋`-executeMethod`）
  - Windows x64・Mono（Mac から作れる）。先に `tools/sync-engine-dll.sh` を回す
  - 体験版はスクリプトの define で作り分ける
- **シェーダが抜け落ちるのを防ぐ**：DuelStage 系の4本は `Shader.Find` だけで読んでいるので、製品ビルドで消える恐れがある
  - 4本を Always Included Shaders に入れる
  - `Assets/KokoSim/Match/DuelStageRig.cs:4581` に null の確認を足す
- 製品ビルドから外すもの
  - Shooter・Probe などの撮影用スクリプトと DebugBridge・F1 HUD（`#if` で囲う）
  - テンプレの残り（`Assets/TutorialInfo`、`Assets/Readme.asset`）
- 起動時のフレーム設定を一本化する
  - `Assets/Scripts/Bootstrap/FrameRateGuard.cs` と `Assets/KokoSim/AppBootstrap.cs` が vSync を逆向きに設定している
- **ベンチマークモード**を作る：起動引数 `-benchmark` で、固定シードのまま次を自動で回し、CSV に出す
  - 新規開始 → 週送り N 回 → 大会日 → 甲子園の試合（満員・守備場面）
  - 出す値：起動時間・ロード時間・週送りの時間・大会日の待ち・fps の分布・GC のメモリ最大値
  - 同じ手順を2台の機で比べられる（「実機確認はシナリオで」の方針どおり）
- 計測の結果から推奨スペックを決める。要るなら軽量設定を作る

### 段階2：製品として最低限の作り
- **設定画面**
  - 解像度、ウィンドウ／フルスクリーン、ウィンドウの大きさ変更、画質（標準／軽量）、fps の上限、音量（BGM・効果音・実況）、実況のオンとオフ
  - 実況のオンとオフは PlayerPrefs のキーが既にあるので、それにつなぐ
  - 見せ方はユーザーと決める（UIの勝手な決定禁止）
- 解像度：既定の 1024×768 固定をやめ、16:10 や横長の画面でも崩れないか確かめる
- **安全な保存**：`SaveGameIO` を「一時ファイルに書いてから置き換える」形にする（途中で落ちても壊れない）
- **固まり対策**：Q30（`BackgroundGameOp` が戻らないと何も起きなくなる）に見張りを足す
- 不具合報告の窓口：ログの場所を案内する
- **権利の処理**
  - 実況の VOICEVOX:No.7 の商用許諾を取るか、声を差し替える（今は未取得で、これが止め札）
  - Meshy で作った6メッシュのプランを確かめて、クレジットに載せるか差し替える
  - On-Jin のクレジット条件を確かめる
  - ゲーム内に**クレジット画面**を作る（`CREDITS.md` を元にする）
- **実名の差し替え口**：甲子園・センバツ・明治神宮大会・球場名を1か所（data/ の YAML）に集め、架空名に切り替えられるようにする
- 生成する校名に**実在校の除外リスト**を入れる（明徳義塾などの組み合わせが出ている）
- **チュートリアル**：最初の数週を案内する最小限のもの。中身はユーザーと決める
- 残っている issue（#1085 と、ラベルの無い5件）に範囲ラベルを付けて片付ける

### 段階3：ストアページを公開する（近日公開）
- ページの素材：カプセル画像（各サイズ）、スクショ5枚以上、トレーラー、説明文、タグ、動作環境
- **AI生成物の申告**：Suno の曲・Meshy と Tripo の装備・VOICEVOX の声
- 年齢区分のアンケートに答える
- Valve の審査は数営業日かかる
- ここからウィッシュリストを集め始める（SNS での告知も）
- 元祖のタイトル名は、作者の許可が無い限りストアや宣伝に使わない

### 段階4：Steam の体験版（2年目の夏まで）
- **区切り**：「2年目の夏の大会（甲子園を含む）が終わった時点」を判定する関数を engine に置く（純C#で、単体テストする）
  - 週送りの処理（Shell の `GameClock` まわり）で、体験版のときだけこの関数を見る
- **終了画面**：「体験版はここまで」とウィッシュリストへのボタン（Steam オーバーレイからストアを開く）
  - 中身はユーザーと決める
- **セーブの引き継ぎ**：区切りの時点でセーブさせ、製品版はそのセーブを読んで続きから遊べる
  - 体験版は区切りの先へは進めない
  - 同じ `SaveCodec` を使うので、追加の変換は要らない
- **Steamworks の最小連携**（Steamworks.NET・MIT）：起動の確認、オーバーレイ、ストアページを開く
- 配信：体験版は別の App ID で、無料・追加費用なし。steamcmd で上げる（Mac でも動く）→ 審査
- Next Fest は1作につき1回しか出られない。出るなら、ストアページを1〜2か月出したあとの回に申し込む
  - 締切は開催の約6週間前で、その時点でストアページが公開されている必要がある

### 段階5：ブラウザで遊べる体験版（いちばん大きな工事。段階4のあと）
- **スレッドを使わない形に**：ブラウザ版では C# のスレッドが使えない
  - `Task.Run`・`Parallel.For`・`Task.Wait` を使っている約20ファイル（`NationBackgroundSim`、`AutumnBackgroundSim`、`GameSession`、`GameClock`、`TrajectoryTableWarmup`、engine の `PrefetchRunner` など）の裏の仕事を、1つの入口（スケジューラ）にまとめる
  - 入口の実装は2つ用意する：Windows はスレッド、ブラウザはフレームごとに少しずつ回す
  - メインスレッドでの `Task.Wait` は、待ち画面を出して非同期で待つ形に直す
  - **並列でも直列でも同じ結果になるか**を、決定論の指紋（`tools/regen-determinism-baseline.sh`）と、直列と並列を比べるテストで確かめる
- **YAML の読み込みを直す**：`streamingAssetsPath` を直接ファイルとして読んでいる10か所（`StadiumCatalogProvider` や `EventTableProvider` など）を、起動時にまとめて読む形か TextAsset にする（両方のプラットフォームで同じ作り）
- **容量を削る**（目安 200〜300MB 以下。itch.io は展開後の合計 500MB・1ファイル 200MB が上限とされる）
  - 球場は標準と甲子園だけにし、ほかは既にある「標準を伸ばす」代わりで出す
  - フォントのアトラスを小さくする（Steam 版の容量も減る）
  - 音声を圧縮する
  - Brotli で圧縮する
  - IL2CPP の削りすぎを防ぐ `link.xml` を用意する
- **描き方**：ブラウザ用の URP 設定を別に作る（SSAO なし・影は軽く）
- セーブはブラウザの中（IndexedDB）に入る。製品版への引き継ぎは、セーブの書き出しと読み込みを付けるかどうか、あとで決める
- 置き場所は unityroom か itch.io（unityroom の容量上限は未確認）。対象は PC のブラウザだけ
- 大会日の待ちは1コアになるぶん長くなる。ベンチマークモードで測り、待ち画面で見せ方を工夫する

### 段階6：製品版の仕上げ → 発売
- 体験版の感想を反映する
- Steam Cloud（Auto-Cloud なら設定だけで、コードは要らない）
- 最終計測で動作環境を確定する
- 価格と発売日を決める
- 近日公開の状態を**2週間以上**出してから発売する。ビルドも審査を受ける
- 実績は任意（発売後でもよい）

### 段階7：発売後
- パッチ：Steam のベータブランチで先に試す。セーブの互換は `SaveCodec` のバージョンで守る
- 英語化・Mac 版・Steam Deck 対応を検討する

## 決めること（ユーザー判断が要るもの・急がない順）
1. 新しいタイトル（段階0。これが段階1の社名・製品名を決める）
2. 公開リポジトリを非公開にするか（製品のコードが丸見えになっている。非公開にすると CI の無料枠の分数を使う）
3. 設定画面・終了画面・チュートリアルの見せ方（それぞれ着手するときに）
4. 価格（段階6）

## 確かめ方
- 段階1：Windows 実機で製品ビルドが起動し、タイトル → 新規開始 → 試合まで通る。シェーダが抜けて落ちない。ベンチマークの CSV が2台で取れる
- 段階4：区切りの関数の単体テスト（1年目の夏は通す・2年目の夏の終わりで止まる）。撮影レシピで区切りの直前から通し、終了画面が出て、そのセーブを製品版で読んで続きから遊べる
- 段階5：決定論の指紋が変わらない（直列と並列で一致）。Chrome・Edge・Safari で起動し、容量が目安以内、2年目の夏まで通せる
- engine を触る段では `dotnet test engine/ -c Release --filter "Category!=Heavy"`。Assets を触ったら `bash tools/check-unity-compile.sh`
